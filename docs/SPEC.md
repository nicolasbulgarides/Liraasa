# Liraasa Workbench — Build Specification

Version of this spec: 1.1 (revised against lexicon 1.0, 16 October 2026)

Originally written against 0.8-rc2. The canonical data is now **Liraasa 1.0**;
every count and schema claim below has been checked against
`data/source/liraasa_1_0.json`. The data formats live in `docs/SCHEMA.md` and
are not repeated here. The corrections are recorded in ADR-0001.

## 1. Purpose

One local web application that is, at the same time:

1. **A codex**: browse, search and read every headword, form, gloss, function word,
   grammar rule, ruling, example and text in Liraasa.
2. **A translator**: English → Liraasa and Liraasa → English, with every output checked
   against the lexicon and grammar.
3. **A learning system**: structured lessons, drills and spaced review that teach the
   grammar from the ground up.
4. **A command center for the language's evolution**: view any word as its ingredients
   (roots, forms, suffixes), and add, respell, retire or replace roots with a full impact
   preview. Every stored text, example and lesson updates automatically and correctly.

The single author is Nicolas. There is one user, on one machine, working in Chrome or
Edge. Design for that, but keep the seams (storage, translation provider, packaging)
replaceable.

## 3. The data

**`docs/SCHEMA.md` is the data reference.** It records the observed 1.0 schema
field by field, with every count, and is kept current. This section states only
what the engine must be built to handle, and does not duplicate it.

The shape, in one paragraph: 26 top-level keys; **1099** headwords (386 primal
roots, 713 compounds, no `Root` type); 7693 form strings, all distinct, of
which **4608** glosses read `"— (unused)"`; **149** function words, 8 pronouns,
36 correlatives, 43 time rows (40 distinct forms), 9 colour families, 4
discourse particles; **452** examples of which 447 are live; 387 rhyme
families; 509 legacy form mappings; **24** validator checks.

Things that will catch out an implementation that assumes a cleaner schema:

- **`protected: true` on every headword.** No canon spelling is ever
  regenerated by rule. The generator proposes; a mismatch is a finding.
- **`english_synonyms` is an array on all 1099 entries.** No semicolon strings.
- **Every compound has exactly two `components`**, and its spelling equals
  `components.join('')`. One compound is **nested**: `mudusomubiti` is
  `mudu` + `somubiti`, itself `somu` + `biti`. The engine must handle nesting,
  and now has a real case to test against.
- **Four compounds' components were inferred** by the 1.0 build from their
  spelling, because the 0.8 record did not list them: `kronobio`, `lumivera`,
  `mavopago`, `mavolumi`. Show them as inferred, per `changelog_1_0`.
- **`mavopago` is the fixed word "society".** Show its ingredients with a badge
  saying so and that `mavo + -pago` is blocked as a productive derivation.
- **`forms` is stored in two key orders**; 80 entries put `verb` second.
  Export preserves each entry's own order (ADR-0002).
- **32 spellings live in more than one namespace** — `maivo` is both a pronoun
  and a root. A form index maps a spelling to a *list*, never one entry.
- **Colour words are their own closed class.** None of the 45 colour spellings
  is a headword.
- **`migration_forms.kind` has five values**, not two: `retired`, `respelled`,
  `merged`, `rewritten` and `archived-phrase`. The last is the awkward one —
  five archived compounds map forward to a **multi-word phrase**, so the target
  is not a single form and cannot be looked up.
- **Watch the characters.** `≤0.7` in `since` (U+2264) and the em dash in
  `"— (unused)"` (U+2014) must survive a round trip byte for byte.
- **Two sections still use workbook column names**: `colors` and
  `numbers.rules` (and `legacy.editorial_notes_0_7` inside `legacy`). The
  other 23 are normalised.
- **Ruling ids collide.** `G1`–`G8` are defined in both `rulings_1_0` and
  `rulings_0_8_carried` with different content, so every reference is
  edition-qualified: `"1.0:G19"`, `"0.8:R2"` (ADR-0004).
- **The eight 0.8 open questions are closed** in
  `settled_open_questions_0_8`. Read them rather than re-asking. In
  particular: transitivity is **usage-based**, so the `gome` check is
  implementable and **no `transitive` field should be added**; ordinals
  (`NUMBER-ne`) and fractions (`NUMBER de NUMBER`) are canon; a derivation
  never combines with a form.

**Rules blocks.** There is no `rules` key. The content is split across
`phonology`, `morphology` and `grammar`. Load them as data, and also keep the
typed rule config in `src/core/config/`; a test asserts the two agree.

**One known error in the data.** `phonology.protected_exceptions` says
"36 amor- double-a roots (legacy canon)". They are compounds, not roots, and
the count is the 0.8-rc2 one: 1.0 has **39** (20 ending `-amor`, 19 beginning
`amor-`), because 1.0 added `amorpeli`, `amorserbu` and `amorvorba`. The
corrected list is in `src/core/config/phonology.ts`; the label is scheduled for
repair in 1.1.

## 4. Stack and architecture

- **Vite + TypeScript (strict) + React.** A static build that runs locally. React is
  chosen because it's the most maintainable option for AI-assisted development; the
  UI is a thin shell, so it could be replaced later without touching the core.
- **Vitest** for tests. **ESLint** with an import-boundary rule. **Prettier.**
- Hash-based routing so the build also works when served as static files.
- No heavy UI kit. Plain CSS with custom properties (design tokens), light and dark
  themes, one shared component set in `src/ui/components/`.
- Pin dependency versions. Prefer mature, widely used libraries.

## 5. Core engine

### 5.1 Morphology

- Generate the seven forms from a spelling using the verb rule, checked in order: `opi`
  → `opioa`; starts with `n` → `-nia`; starts with `s` → `-sia`; starts with a vowel →
  `-a`; otherwise → first consonant + `a`. Only the first letter of the whole word counts
  (so compounds take the class of their modifier).
- Suffix order: root → one form or derivation (`-yo`, `-vu`, `-pago` attach to the root,
  not a verb form) → `-ti` → `-ri` (always last). `-ti` may attach to personal names
  (R12). `mavo + pago` is blocked.
- Protected spellings are never regenerated. **`protected: true` is already on every
  1.0 headword** (settled question 8), so it is the author's field, not an additive one.
  The generator proposes; it never overwrites.
- Concatenation is literal. There is no elision, so `dorva + asa` is `dorvaasa` with a
  double `a`.
- **Golden test:** regenerate all 1099 × 7 = 7693 forms and compare with the stored
  forms. **Verified: zero mismatches**, and all 7693 are distinct. Any future mismatch
  is a test failure that lists the words; it is reported, never auto-corrected.

### 5.2 Parser

Follow the Codex: **lexicon-first, never blind suffix stripping.** Many roots end in
letters that look like suffixes (`navu`, `sevu`, `trana`, `pago`). Algorithm: exact
lookup in the form index → longest known word, then the closed list of endings → `-ti`
→ `-ri`. Also recognize function words, pronouns (with `-ri`), discourse particles,
correlatives (`ki-coda`…), hyphenated numbers (`dossacenta-unzira-penta`), ordinals
(`una-ne` — the `ne` after a number is never negation), time words, colour words (their
own closed class) and proper names. Return **all** valid parses, ranked, never just the
first. Preserve capitalization and punctuation as token metadata.

A spelling may belong to several namespaces at once (32 do), so a lookup returns a set
of candidates. A pre-1.0 spelling resolves through `legacy.migration_forms` under ruling
1.0:G19 — and for five archived compounds the target is a **phrase**, not a form.

Output an interlinear gloss: surface / segmentation / gloss per morpheme / free gloss.

### 5.3 Lexicon validator

Port the **24** checks from `validate.py`, whose two helper modules are missing, so the
port reimplements them. Results must match `validation_1_0.json` exactly on 1.0 — 24
PASS, 0 WARN, 0 FAIL — as a golden test. Each check is a separate function with its own
tests. Checks 16 and 17 are WARN-on-finding; the rest are FAIL-on-finding.

Support the baseline comparison (checks 12 and 13) against a previous edition and a
corpus run (checks 14, 15, 21) against all stored texts. **Check 12 cannot run** until
`lexicon_0_8_rc2.json` arrives; it reports `FAIL / "not executed"`, exactly as
`validate.py` does, rather than silently passing.

The app also **runs the checks before every save** (ADR-0007): a save that would
introduce a FAIL is refused and reported. Expose the same code as `npm run validate`.

### 5.4 Sentence checker

The validator proves lexical validity, not grammaticality. Check the **20-slot** 1.0
clause template (SCHEMA §1.7.1), not the 10-position 0.8 one:

```
[FRAME] [TOPIC hozi] SUBJECT [TENSE] [noma] [ne] [MODAL] [APPROACH] [PHASE]
[EFFORT] [ASPECT] [ITERATION] [EVIDENTIAL] VERB [OBJECT] [ADJUNCTS] [fuyi]
[hoyo|yasmo] [ATTITUDE] [ki]
```

Every preverbal operator scopes over everything to its right (1.0:G1); at most one word
per slot, with the 13 exclusions in `grammar.stacking`; tense before `noma` before `ne`;
one evidential per clause; `hoyo`/`yasmo` before the attitude marker and never together;
attitude words and `ki` clause-final only (1.0:G22), with `zoke` never beside a
certainty marker (0.8:R9); `-ri` only on nouns and pronouns and always last; `sige`
clauses carry their own tense (0.8:R6); a non-final `raho`-clause closed by a comma
(1.0:G21); `fuyi` only with a plural or coordinated subject; `kroti` used as a
preposition, not a conjunction; `-asa` not used as "very"; poetic omissions only in
poetic mode.

**`gome` is now checkable.** Transitivity is usage-based (settled question 5): `gome`
may passivise any verb used with an object in its clause, and a verb used without one
cannot take it. No lexical flag is needed and none should be added.

Every finding has an **edition-qualified** rule id, a message, the span, a severity
(error / warning / note) and a link to the relevant grammar entry. Register-aware:
ascended forms used irreverently are a text-level tone, never an error.

### 5.5 Generators

Correlatives (determiner × concept: a complete 6 × 6 grid), numbers 0–999,999,999 with
the hyphenation and group rules, colours (9 bases × 4 modifiers), and time words
(`merno`/`vesno`/`nullo` + `pressa`/`futu`; there is no `po` series, so do not offer
one). Each is tested against the values stored in the JSON.

**Verified:** all 1000 entries of `numbers.lookup_0_999`, all 36 correlatives in
storage order, all 45 colour words, and the 6 time-of-day words match.

## 6. Data model

### 6.1 Canonical JSON and additive fields

The working lexicon stays in the author's schema so his other tools keep working.
The app may add **only additive, namespaced fields**, documented in `docs/SCHEMA.md`:

- `id`: a stable identifier for every headword, function word and other entry, assigned
  once on first import and never changed. Spellings change; ids don't. This is what
  makes root swaps safe.
- `retired`: `{ in_edition, replaced_by?, reason }` for retired entries (§6.5).

`protected` is **not** additive: the author already ships it as `true` on every
headword.

**Where `id` lives depends on the edition** (ADR-0008). 1.0 is released and frozen, so
its ids go to the `data/lexicon/ids.json` sidecar and the canonical file is written
byte-identically. From 1.1 on, `id` is written inline.

Export must reproduce the original structure, **each entry's own key order**, value
shapes and every unknown field. One field map per section drives both directions, so
importer and exporter cannot drift (ADR-0002).

**Round-trip test:** import 1.0 → export → import again → deep-equal, and the
serialised output is **byte-identical** to the file on disk, trailing newline included
(there is none). At 1.1 the only difference is the inline ids; stripping them gives back
the source exactly. **Verified.**

### 6.2 Internal model and indexes

Typed records for each section. Build in-memory indexes on load — the full list is in
ARCHITECTURE §2 — covering: form → **a list of** (namespace, entry id, slot), since a
spelling can belong to several namespaces; root → compounds using it as modifier or
head; root → derived words; English synonym and gloss → entries; rhyme ending → words;
entry id → texts, examples and lessons that use it; pre-1.0 spelling → its 1.0
replacement; reserved spelling → why.

All rebuild in well under a second at current size (7693 forms plus derivations and the
closed classes, 11,235 distinct spellings indexed). **Verified: import plus every index
in about 140 ms.**

### 6.3 Search

Instant search across spelling, any form, gloss, synonyms, domain and notes, with
filters for type, status, register, domain, edition and "has unused slots".

### 6.4 Texts as token documents

Every stored writing (songs, the Narvolore story, Bumrepago, examples promoted to
texts, the author's new writing) is saved as **structured tokens**, not plain text,
so a root change re-renders everything correctly:

```json
{
  "id": "text_vorbalira",
  "title": "Vorbalira ala Melodia",
  "kind": "song",
  "register": "sacred",
  "tone": "plain",
  "edition_written": "0.8",
  "sections": [
    {
      "label": "Verse 1",
      "lines": [
        {
          "tokens": [
            { "t": "lex", "entry": "<headword id>", "slot": "verb", "sfx": [], "cap": true },
            { "t": "fn", "entry": "<function word id>" },
            { "t": "name", "value": "Melodia" },
            { "t": "punct", "value": "," }
          ],
          "en": "English translation of the line",
          "surface_snapshot": "the line exactly as it rendered when last saved"
        }
      ]
    }
  ]
}
```

Token types cover lexical words (entry id + slot + derivation + suffix stack),
function words, pronouns, particles, correlatives, numbers (stored as a value),
time words, colours, proper names (a names registry), punctuation, line breaks, and
`unknown` (raw text, always flagged). When importing plain text, run the parser; if a
word has several parses, ask the user to choose and remember the choice. The
`surface_snapshot` lets the app show exactly what changed after a language edit.

**Registers are two different vocabularies.** A *text* is `everyday`, `poetic` or
`sacred`; an *entry* is only `everyday` or `poetic`, because by ruling 0.8:R10 there is
no sacred word list. A token counts as sacred because of its form — an ascended slot
(`-asa`, `-asasan`) or a divine title (`li X-asasan`). `tone: "irreverent"` is a
separate, optional text-level flag for ascended forms used ironically
(`bumreasasan`, `Narvoasa!`); it is never written into the lexicon.

### 6.5 Changes, changesets and undo

The app owns the canonical JSON (ADR-0007), so every edit it makes must be traceable.
Every edit is a **changeset**: an ordered list of operations, each recorded with
`slot`, `from`, `to`, `ruling`, `added_in` and `reason` — the shape ruling 0.8:R2 names
— plus `entry` (a **stable id**, never a spelling), `op`, timestamp and author.

The `authorized_changes` field this shape came from no longer exists in the data; R2
still describes the mechanism, so the shape is ours to define (ADR-0001, finding 11).
A record with no reason is rejected. Operations:

- add root · add compound · edit gloss · edit metadata
- **respell root** (cascades to its forms, compounds and derived words)
- **retire root**, optionally **replace with compound** (the author's current workflow:
  cutting roots that can be expressed as compounds). Retired entries stay in the data
  with `retired.replaced_by`, so old texts still resolve until migrated.
- activate unused slot (requires a reason **and** a ruling reference, per 0.8:R2)
- merge entries · split entry

Changesets are applied atomically, can be undone, and generate the changelog. **The
validator runs before every save**; a save that would introduce a FAIL is refused and
reported. `data/source/validate.py` stays in the repo as an independent second opinion
on whatever the app writes.

### 6.6 Editions

An edition (`1.0`, `1.1-draft`…) has a status (`released` / `working`) and policies.
Policies are data, enforced by the change engine with a clear message, and can be
overridden only by an explicit, logged author action. Released editions are read-only
snapshots; baseline comparison uses the previous released one.

**1.0 is released and frozen. Work happens in `1.1-draft` with 1.0 as baseline**
(ADR-0008). The live policy is the reserve: 497 spellings are reserved, retired roots
reusable from 2.0 and respelled ones never. The 0.8 policy "R3 freezes the Root Review
queue" is spent — the queue closed in 1.0.

Two decisions are deferred to 1.1 and belong in the Open questions module, never to be
resolved by the tool: restoring `lalma` and `sanlu` (needed for *Bumrepago*), and
possibly restoring `rohu`, `sabire` and `sonsa` (which would avoid re-recording songs).
All five are currently reserved, so restoring any of them means overriding the reserve
policy by a logged author action.

## 7. App modules

Each module is a folder in `src/ui/modules/` with its own route, and talks only to
`src/core` and `src/storage`. A global command palette (Ctrl+K) reaches every word,
text, lesson and action.

1. **Dashboard**: edition, counts, validator status, open questions, recent changes,
   learning streak.
2. **Lexicon**: searchable table and entry pages. An entry page shows all seven forms
   with glosses (unused slots shown as unused), synonyms, register, status, editorial
   notes, history of changes, rhyme family, and everywhere it's used.
3. **Root Lab (ingredients view)**: any word broken into its parts as chips (modifier,
   head, form ending, derivation, `-ti`, `-ri`), with each chip linking to its entry. A
   root page shows its family tree: forms, compounds using it, derived words, texts,
   examples, lessons, rhyme family. Badge what the data knows: components the 1.0 build
   **inferred** from the spelling (`kronobio`, `lumivera`, `mavopago`, `mavolumi`), and
   **fixed words** whose split is etymological rather than productive (`mavopago` is
   "society"; `mavo + -pago` is blocked). **Editing:** respell, retire,
   retire-and-replace,
   add. Before applying, an **impact preview** lists: every form that changes; every
   compound and derived word that changes, including **verb-class changes** when a first
   letter changes; new collisions with any form, function word, pronoun, number,
   correlative or time word; proximity and phonotactic violations for the new spelling
   (two syllables, consonant start, vowel end, no initial cluster except kr/tr, at least
   two edits from everything, declared exempt pairs allowed); every text line whose
   surface changes, shown as a before/after diff; rhyme families gained and lost, and
   **rhyme families that stop rhyming** (this matters for songs — 1.0 has no
   `rhyme_pairs` section, so compute pairs from `rhyme_families`); examples and lessons
   affected. For the 40 Root Review roots, prefill the stored candidates and their
   rationales. Apply is a single explicit action that creates a changeset.
4. **Codex (texts)**: reader and editor for token documents, with interlinear view on
   demand, register tags, per-line English, and live checking as you type (lexical and
   sentence checker). Unknown words get a quick action: "build a compound from existing
   roots" (proposal, flagged noncanonical) or "add to open questions". Never "invent".
5. **Translator**: see §8.
6. **Learn**: see §9.
7. **Grammar reference**: the grammar sections, rulings R1–R12 and G-rulings, the
   clause template, function words, pronouns, correlative grid, numbers, colours and
   time words, all rendered from data with live examples.
8. **Validate**: runs the 15 checks and the corpus run, shows results grouped by check,
   with links to the entries involved.
9. **Changes & Editions**: changeset history, diffs, undo, edition policies, changelog
   preview and export.
10. **Open questions**: every item the author must decide (the three unconfirmed
    compounds, transitivity, ordinals, Root Review, vetoes, anything the tool flags),
    each resolvable only by an explicit author action that gets logged.
11. **Settings**: storage folder, theme, translation provider and API key, export
    formats.

## 8. Translator

A `TranslationProvider` interface with two implementations:

- **Rule-based (default, offline):** Liraasa → English by parsing and interlinear
  glossing. English → Liraasa as an assisted composer: find candidate words through
  the synonym and gloss index, let the user pick, and assemble the clause in template
  order with tense, negation, modal, aspect, evidential, certainty and question
  controls. The output is guaranteed valid because it's assembled from the lexicon.
- **LLM-assisted (optional):** calls the Anthropic Messages API from the browser with
  the user's own API key (stored locally, never in the repo or the exported data; uses
  the `anthropic-dangerous-direct-browser-access` header). The model id is a setting,
  not hardcoded. The request includes the Quickstart rules and a relevant slice of the
  lexicon (words matched from the English input). **Every LLM output is tokenized,
  parsed and checked before it's shown.** Unknown words, invented roots and grammar
  violations are highlighted, with a "retry with these errors" action. A free-form
  output is never saved as canonical without passing checks.

Both directions show alternatives, the interlinear breakdown, and which register was
used. Translations can be saved as token documents.

## 9. Learning system

- **Lessons are data** (`data/lessons/*.json`), referencing entries by id so they update
  automatically after a language change. A lesson has: id, title, prerequisites,
  objectives, explanation blocks (Markdown with embedded live examples), and exercises.
- **Curriculum outline** (draft the lessons from the Codex and Quickstart; the author
  reviews them): sounds and stress → the seven forms → the verb rule → suffix order and
  derivations → compounds and reading words apart → the noun phrase → pronouns and
  demonstratives → the clause template and tense → negation → modals and aspect →
  evidentials and certainty → questions and correlatives → linking and time clauses →
  voice, causative, reciprocal, nominalization → conversation particles → degree and
  comparison → numbers, time, colour → the three text registers → poetry, song and
  performance.
- **Exercise types**, each generated from live data: build a form from a root; identify
  the slot of a form; apply the verb rule; segment a word into its parts; order the
  particles (drag and drop, keyboard-accessible); fix a sentence with one error; choose
  the right "to be" (ke/ka/kapoki/loya/miyo); translate a short sentence either way;
  read a song line interlinearly; rhyme finder.
- **Exercise generators must only use real entries and canonical meanings.** Never
  quiz an unused slot for a meaning.
- **Spaced repetition** with FSRS or SM-2 behind a `Scheduler` interface. Progress is
  stored per learner. Design for more than one learner profile, since lessons may later
  be shared with students.

## 10. Storage and persistence

A `StorageAdapter` interface with:

- **FileSystemAccessAdapter** (primary): the user picks the project folder once; the app
  reads and writes `data/lexicon`, `data/texts`, `data/lessons` and `data/changes`
  directly, so everything lives in git. Remember the folder handle in IndexedDB and
  re-request permission on load.
- **IndexedDBAdapter**: autosave of unsaved work and learner progress.
- **Export/import** of a single bundle as a fallback.

Keep the interface ready for a later Tauri desktop adapter. Writes are atomic (write
temp, then replace) and every save of the lexicon writes a timestamped backup.

## 11. Exporters

Behind an `Exporter` interface: canonical lexicon JSON; changelog (Markdown); the
machine-readable quickstart JSON for other language models; a texts bundle; and
(later) the workbook. Exports are deterministic so git diffs stay readable.

## 12. Quality bar

- **Golden tests:** all 1099 headwords' forms regenerate (**green**); validator output
  equals `validation_1_0.json`; lossless byte-identical round-trip (**green**); ids
  stable across a respelling (**green**); the twelve validated Quickstart sentences, the
  447 live examples, the demonstration corpus, *Bumrepago* and the six songs parse with
  no unknown words (proper names excepted); generators match stored correlatives,
  numbers, colours and time words (**green**).

  For the songs, test at word and parse level only: the supplied
  `corpus/legacy_0_8/song_*.txt` have every line but **scrambled line order**. Any
  order-dependent test waits for the 0.8 codex PDF.
- **Change engine tests:** respelling a primal root updates its forms, every compound
  using it, every derived word and every text, and undo restores the original exactly;
  a first-letter change that alters verb class is reported; a respelling that creates a
  collision is blocked with a clear message; retiring a root keeps old texts resolvable.
- **Accessibility:** WCAG 2.2 AA. Full keyboard operation, visible focus, screen-reader
  labels on chips and drag-and-drop exercises (with a keyboard alternative), reduced
  motion respected, no information conveyed by colour alone.
- **Performance:** the app loads the full lexicon and indexes in under one second
  (**measured: ~140 ms for import plus every index**); search responds as you type.
- **Typography:** a clear sans for UI, a readable serif or display face for Liraasa text,
  generous size for vowels; spelling is never altered for display.

## 14. Decisions the tool must not make

Surface these in the Open questions module; never resolve them in code:

- Any new root, any new gloss, any activation of an unused slot (0.8:R2 requires an
  author decision and a ruling reference).
- Any respelling, any retirement, any veto.
- Overriding an edition policy — in particular the reserve, which holds 497 spellings.
- **The two decisions deferred to 1.1:** restoring `lalma` and `sanlu` for
  *Bumrepago*; possibly restoring `rohu`, `sabire` and `sonsa` to avoid re-recording
  songs.
- Anything the tool flags as a finding but cannot resolve: an unknown word in a text, a
  parse the user must choose between, a `WARN` from check 16 or 17.

**Already settled — read `settled_open_questions_0_8`, do not re-ask.** All eight 0.8
questions are closed: the meanings of `nevlosolo`, `kronobelda` and `marelirbu` are
REDEFINED with literal 1.0 readings; no 0.8 addition is vetoed; the Root Review queue is
closed; derivations never combine with forms; transitivity is usage-based and **no
`transitive` field should ever be added**; ordinals and fractions are canon; motion
prefixes are a closed list; every headword carries `protected: true`.

The Open questions module shows these as settled, with their answers, and keeps its live
list to the items above.
